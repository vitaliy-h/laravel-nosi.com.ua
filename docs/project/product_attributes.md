# Динамічні параметри товарів (характеристики + фільтри)

> **Статус: специфікація, не реалізовано.** Нічого з описаного нижче в коді ще немає
> (перевірено 2026-09-05: таблиць `shop_product_attributes` і супутніх класів у проєкті не існує).
> Читати як план робіт, а не як опис поточної поведінки.

## 1. Задача

Дати можливість менеджеру з адмінки:

1. створювати довільні параметри товарів (RAM, діагональ, колір, матеріал, вага…);
2. прив'язувати різні набори параметрів до різних категорій — товари категорії отримують у формі саме її параметри;
3. заповнювати значення параметрів у картці товару;
4. фільтрувати каталог за цими параметрами, з підрахунком кількості товарів по кожному значенню (як зараз працює фільтр брендів).

Все — без деплою і без участі розробника.

## 2. Обране рішення

**Окрема таблиця значень `shop_product_attribute_values`, один рядок на товар, окрема справжня колонка на кожен параметр.**

При створенні параметра в адмінці в цю таблицю додається колонка з іменем `a{id}`, де `id` — первинний ключ рядка з `shop_attributes`.

### Чому не EAV (рядок на кожне значення)

Фільтрація по N параметрах в EAV — це N підзапитів `EXISTS` до однієї таблиці, і планувальник не має статистики, щоб побудувати адекватний план. Тут фільтр по будь-якій кількості параметрів — це **один `JOIN` і звичайний `WHERE` по індексованих колонках**:

```sql
SELECT p.* FROM shop_products p
JOIN shop_product_attribute_values v ON v.product_id = p.id
WHERE p.category_id IN (...) AND v.a17 >= 8 AND v.a23 IN (5, 9) AND v.a31 = 1
```

### Чому окрема таблиця, а не колонки прямо в `shop_products`

- `shop_products` лишається стабільною, її схема повністю описана міграцією в git;
- DDL ізольований в одній таблиці — менша зона ураження, адмінка товарів не ламається від невдалого `ALTER`;
- ліміт розміру рядка InnoDB (~8126 байт) витрачається тільки на параметри, а не ділиться з `text`/`meta_*` полями товару;
- таблицю значень можна перебудувати або очистити, не чіпаючи товари.

### Чому імена колонок `a{id}`, а не слаг параметра

Ім'я походить від цілочисельного PK, тому:

- у DDL не потрапляє користувацький ввід — жодного ризику інʼєкції чи зарезервованих слів;
- неможливі колізії з наявними колонками;
- перейменування параметра менеджером **взагалі не чіпає схему**;
- унікальність гарантована первинним ключем.

Для читабельних URL фільтрів використовується окреме поле `code` (`?ram=8,16`), а не імʼя колонки.

## 3. Схема БД

### 3.1 `shop_attributes` — довідник параметрів

| Колонка | Тип | Призначення |
|---|---|---|
| `id` | bigint PK | джерело імені колонки |
| `title` | string | назва для користувача («Обʼєм памʼяті») |
| `code` | string unique | ключ у URL фільтра (`ram`) |
| `type` | enum | `string` / `number` / `bool` / `select` / `multiselect` |
| `unit` | string null | одиниця виміру («ГБ», «см») |
| `is_filterable` | bool | показувати у фільтрах каталогу + вішати індекс |
| `is_visible` | bool | показувати в характеристиках на сторінці товару |
| `rank` | int null | порядок у формах і фільтрах |
| `column_name` | string null | `a{id}`, заповнюється при створенні колонки |
| `column_created_at` | timestamp null | маркер того, що колонка реально існує |
| `archived_at` | timestamp null | мʼяке видалення |
| `timestamps` | | |

`column_created_at IS NULL` означає «параметр створений, колонки ще немає» — такий параметр не показується ні у формах, ні у фільтрах.

### 3.2 `shop_attribute_options` — значення для `select` / `multiselect`

`id`, `attribute_id` (FK cascade), `title`, `rank`, `timestamps`.

### 3.3 `shop_category_attribute` — прив'язка до категорій

`category_id` (FK cascade), `attribute_id` (FK cascade), `rank`, `is_required`, unique(`category_id`, `attribute_id`).

### 3.4 `shop_product_attribute_values` — широка таблиця значень

Створюється міграцією **порожньою**, лише з ключем:

```php
Schema::create('shop_product_attribute_values', function (Blueprint $table) {
    $table->foreignId('product_id')->primary()->constrained('shop_products')->cascadeOnDelete();
    // колонки a{id} додаються динамічно
});
```

Один рядок на товар (1:1 розширення `shop_products`). Рядок створюється при першому збереженні значень (`updateOrCreate`).

Мапінг типу параметра на тип колонки:

| `type` | Колонка | Примітка |
|---|---|---|
| `string` | `varchar(255) NULL` | |
| `number` | `decimal(15,4) NULL` | точне порівняння в range-фільтрі |
| `bool` | `tinyint(1) NULL` | |
| `select` | `unsignedBigInteger NULL` | id опції, без FK (динамічна колонка) |
| `multiselect` | — | у широку таблицю не лягає, див. 3.5 |

Індекс на колонці створюється **тільки якщо `is_filterable = true`** — ліміт 64 вторинних індексів на таблицю витрачається інакше непомітно.

### 3.5 `shop_product_attribute_options` — тільки для `multiselect`

`product_id`, `attribute_id`, `option_id`, unique(`product_id`, `option_id`), індекс (`attribute_id`, `option_id`).

Одне значення на рядок. Фільтр по multiselect — `whereExists` до цієї таблиці. Етап 4, за потреби.

## 4. Життєвий цикл параметра

### 4.1 Створення

DDL у MariaDB **не транзакційний** (неявний коміт), тому порядок операцій жорстко заданий і збій завжди відновлюваний:

1. Менеджер зберігає форму → створюється рядок у `shop_attributes`, `column_name = 'a'.$id`, `column_created_at = null`.
2. Диспатчиться `CreateAttributeColumnJob` — DDL **не виконується в HTTP-запиті**.
3. Джоба робить preflight-перевірку лімітів, виконує `ALTER TABLE ... ADD COLUMN`, за потреби додає індекс, проставляє `column_created_at`.
4. До цього моменту параметр в адмінці має статус «створюється».

Єдиний можливий збій — «рядок є, колонки немає». Він детермінований і лікується командою звірки (5.1).

Чому джоба, а не прямий `ALTER`: `ALTER TABLE` чекає на metadata lock, і поки він у черзі, **всі наступні запити до таблиці теж стають у чергу**. Виносити це з веб-запиту обовʼязково.

### 4.2 Зміна

- `title`, `unit`, `rank`, `is_visible` — звичайний апдейт, без DDL.
- `is_filterable` — джоба додає або дропає індекс.
- `type` — **заборонено після створення**. Потрібен інший тип — створюється новий параметр, старий архівується. Конвертація типу заповненої колонки може мовчки втратити дані.

### 4.3 Видалення — двофазне

**Фаза 1, з адмінки — архівація.** Проставляється `archived_at`. Параметр миттєво зникає з форм, фільтрів і характеристик. Жодного DDL, повністю зворотно.

Причина: `DROP COLUMN` знищує значення по **всіх товарах одночасно** і без undo. Помилковий клік менеджера = 5000 втрачених значень, відновлення лише з бекапу.

**Фаза 2, командою розробника — дроп.** `shop:attributes-gc` дропає колонки параметрів, архівованих понад N днів. Під наглядом, у передбачуваний момент, з бекапом.

Так звільняється і бюджет індексів: стеля 64 стає «64 одночасно фільтрованих параметри», а не «64 за весь час життя каталогу».

## 5. Artisan-команди

### 5.1 `shop:attributes-sync`

Порівнює `shop_attributes` з `information_schema.columns` і доганяє те, чого бракує: створює відсутні колонки, індекси, проставляє `column_created_at`.

Це ключова команда всієї схеми — саме вона робить її відтворюваною. **Джерелом правди стає таблиця атрибутів, а не самі колонки**, тобто довідник параметрів фактично виконує роль міграції:

- новий розробник: `migrate` → сидер довідника → `shop:attributes-sync` → ідентична структура;
- деплой: `shop:attributes-sync` у `post-deploy`;
- тести: хелпер створює параметр разом з колонкою.

### 5.2 `shop:attributes-gc --days=30`

Дропає колонки (і повʼязані рядки опцій) для параметрів, архівованих понад `--days` днів. Ідемпотентна, виводить план перед виконанням.

## 6. Preflight-перевірка лімітів

Виконується в джобі **до** `ALTER`, з людською помилкою в адмінці замість 500-ї:

| Ліміт InnoDB | Значення | Поріг попередження |
|---|---|---|
| Колонок на таблицю | 1017 | 900 |
| Вторинних індексів на таблицю | 64 | 58 |
| Розмір рядка | ~8126 байт | розрахунок за типами |

MariaDB 11.8 підтримує instant `ADD COLUMN` (з 10.3) та instant `DROP COLUMN` (з 10.4), тому обидві операції не перебудовують таблицю. Ліміту «64 instant-операції, далі rebuild» з MySQL 8.0.29 у MariaDB немає.

## 7. Фільтрація каталогу

### 7.1 Інтеграція з наявним механізмом

Поточна конструкція вже майже готова: `ShopFilterData` → `toApplicable()` → `BuildProductsQuery` викликає `apply()` на кожному фільтрі. Потрібні три зміни.

**1. Явна колонка у фільтр-DTO.** Зараз `InFilterData::apply()` містить хардкод:

```php
$column = $this->key === 'brand' ? 'brand_id' : $this->key;
```

Замінити на явне поле `column` у `InFilterData` і `RangeFilterData` (`brand` → `brand_id`, `ram` → `v.a17`). Той самий DTO обслуговує і статичні, і динамічні фільтри — нові класи не потрібні.

**2. Динамічні фільтри в `ShopFilterData`.** Додати `Collection<string, BaseFilterData> $attributes` (ключ — `code` параметра) і включити її в `toApplicable()`:

```php
public function toApplicable(): Collection
{
    return collect([
        'brand' => $this->brand,
        'price' => $this->price,
        'search' => $this->search,
    ])->merge($this->attributes);
}
```

**3. Один джойн у `BuildProductsQuery`.** Якщо серед активних фільтрів є хоч один атрибутний — додається один джойн на всі:

```php
$query->join('shop_product_attribute_values as v', 'v.product_id', '=', 'shop_products.id')
      ->select('shop_products.*');
```

`select('shop_products.*')` обовʼязковий, інакше колонки значень перетруть поля товару в гідрації.

### 7.2 Побудова списку фільтрів

`PrepareShopFilterQuery` розширюється: для поточної категорії підтягуються прив'язані параметри з `is_filterable = true` і `column_created_at IS NOT NULL`, і для кожного будується DTO:

- `select` → `InFilterData` з опціями і лічильниками: `GROUP BY v.a17` по запиту, з якого виключено цей самий фільтр (точно як зараз для брендів);
- `number` → `RangeFilterData` з `MIN(v.a17)` / `MAX(v.a17)`;
- `bool` → `InFilterData` з двома опціями.

Значення з URL читаються за `code`: `?ram=8,16&color=12,13&weight_from=1&weight_to=5`.

Кожен `select`-фільтр коштує один `GROUP BY`-запит — так само, як зараз бренд. За великої кількості фільтрованих параметрів у категорії це варто тримати в полі зору.

## 8. Адмінка (Filament)

**`AttributeResource`** (група Shop) — CRUD довідника: `title`, `code`, `type`, `unit`, `is_filterable`, `is_visible`, `rank`; опції для `select`/`multiselect` через `Repeater`. Бейдж стану колонки: «створюється» / «активний» / «в архіві». `type` доступний для редагування лише при створенні.

**`CategoryResource`** — Relation Manager для прив'язки параметрів до категорії з порядком і ознакою обовʼязковості.

**`ProductResource`** — секція «Характеристики», схема якої будується динамічно за `category_id` і реагує на його зміну (`live()` + `Get`). Поля не належать моделі `Product`, тому:

- завантаження значень — у `mutateFormDataBeforeFill()`, під префіксом `attrs.*`;
- збереження — в `afterSave()`, через `updateOrCreate` по `product_id`.

Тип поля за типом параметра: `TextInput` / `TextInput::numeric` / `Toggle` / `Select` / `Select::multiple`.

## 9. Тестування

`RefreshDatabase` прогонить міграції, тому таблиця значень у тестах стартує **без динамічних колонок**. Потрібен хелпер, який створює параметр разом з колонкою синхронно:

```php
$attribute = createAttribute(['code' => 'ram', 'type' => 'number', 'is_filterable' => true]);
```

Покрити:

- створення параметра → колонка і індекс існують, `column_created_at` проставлений;
- preflight — відмова при вичерпаному ліміті індексів;
- `shop:attributes-sync` створює колонку для параметра, якому її бракує;
- `shop:attributes-gc` дропає колонку архівованого параметра і не чіпає активні;
- фільтр каталогу: range по `number`, множинний вибір по `select`, комбінація кількох параметрів;
- лічильники опцій рахуються з виключенням власного фільтра;
- архівований параметр зникає з фільтрів і форми товару.

## 11. Відкриті питання

1. **Успадкування по дереву категорій** — чи має параметр, прив'язаний до «Електроніки», автоматично діяти на «Смартфони»? Категорії на nested set, тому технічно це `whereAncestorOrSelf`. Ускладнює лише відображення в адмінці («звідки успадковано»). За замовчуванням у плані — пряма прив'язка без успадкування.
2. **`multiselect`** — чи потрібен на старті. Якщо ні, етап 4 не робимо і схема лишається простішою.
3. **Очікувана кількість параметрів** — від неї залежить, наскільки близько ми до стелі 64 фільтрованих. До ~50 одночасно фільтрованих запас комфортний.
